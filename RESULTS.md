## Methodological findings, logged as they occurred (pre-real-seed)

### 1. Gate-hardening bug (2026-08-21) — corrupted a decision, not a measurement

§2.2 specifies the gate is "trained soft, hardened at inference." The evaluation path (`forward_eval_autoregressive`) never did this — it used the soft gate value throughout, including at the §3.2 competence-gate check. This is a different class of bug from the others found this session (a shrunk cache, a multiprocessing deadlock, a structural shortcut): those corrupted *numbers*. This one corrupted a *decision* — whether a pilot counted as "reached criterion" at all, which everything downstream (S*, the training budget, which checkpoints the causal/query PR were even measured on) was built on top of.

**Magnitude, same checkpoint and held-out batch:** soft-gated accuracy 96%, hard-gated accuracy 77%, at `L=3`. Not a rounding difference — a checkpoint that looked like it had passed had actually failed by 19 points.

**It surfaced only because a stronger check was insisted on.** The immediate task was reporting the accuracy-vs-`L` slope and `P(m|L)` as evidence, not "clear." Computing `P(m|L)` correctly required hardening the gate to get a discrete integration count instead of a soft sum that could hide partial integrations. The bug was found as a side effect of building a more rigorous diagnostic, not by looking for it directly — worth recording as a case for building the stronger check even when the weaker one already reads "pass."

**Consequence:** every "reached criterion" determination in every pilot run this session, before the fix, was measured under the wrong evaluation. All were re-run under the corrected one; only the hard-gated numbers appear in `PREREG.md`.

### 2. Causal-PR / query-PR conflation, in both directions (2026-08-21)

§3.3's original verification criterion compared causal PR (retrieval-logit Jacobian, whole-state output sensitivity) against `rank` (a bound on the query projection specifically) — different objects, confirmed empirically to diverge (pilot 0: causal PR 19.1, query PR 46.3, same checkpoint). Fixing §3.3 exposed that §3.1.5 — which sets `rank` in the first place — had made the identical error in the opposite direction: sizing the rank *from* causal PR, on the stated intent of "measure the dimensionality this mechanism needs and give it that many dimensions," when causal PR was never that quantity for the query projection specifically.

**Both were written by the same process, in the same document, before either was caught.** The self-consistency check that would have caught this earlier — do the two PR measurements on the same pilot actually agree in direction? — wasn't run until asked for. On pilot 2 (the slow, unstable one) they don't just disagree in magnitude, they invert: highest causal PR, lowest query PR of the three pilots. A model that used *more* of its output-sensitive dimensionality used a *narrower* query to do it.

**Consequence:** rank corrected from a wrongly-derived 32 (causal PR) to 48 (query PR, the right quantity) — itself later superseded again (see finding 4) once it turned out none of the checkpoints this was measured on were stable. Final rank: 36. Not a refinement at any step — a different number from a different measurement, twice.

### 3. First-hop reliability floor may exceed §5.3's original target (pre-flagged, not yet a real-seed finding)

Pilot 2, hard-gated, **under the unstable constant-LR recipe**: 6.6-7.2% of arm-A items never open the gate at all (`m=0`), on items that are answerable with no ambiguity. §5.3 originally set a flat 5% false-abstention target with no accounting for a reliability floor independent of calibration. Restated in `docs/phase1.md` §5.3 before real seeds run: target is now 5 points *above a measured floor*, not an absolute ceiling, and the floor itself must be reported as a finding if it turns out to dominate.

**Re-checked against the stable, cosine-schedule pilots (2026-08-22): the floor mostly evaporated.** `m=0` rate at `L=2`/`L=3`: pilot 0, 0.6%/0.5%; pilot 1, 0%/0.1%; pilot 2, 0.35%/0.65%. All comfortably under the original flat 5% target — the 6.6-7.2% figure was itself a symptom of the training instability (finding 4), not an architectural ceiling on first-hop reliability. The floor-relative restatement in §5.3 stays as the more defensible general principle (it would have caught this instead of just describing it after the fact), but the specific number it was written in response to no longer applies to the stable recipe.

### 4. Constant-LR oscillation — none of three pilots ever stably passed (2026-08-22)

Extending pilots past their first criterion pass, to test the causal/query-PR migration in finding 2, surfaced something the migration question didn't anticipate: under `S*`'s corrected definition ("holds at every subsequent evaluation"), **none of the three pilots ever qualified** — including pilot 2, whose own pass at step 7,600 didn't survive to the next check (step 7,700: L2 0.93→dropped, L3 0.96→0.88). All three oscillated 85-97% on a *fixed* validation set indefinitely (same 128 items every check, so the oscillation is the model's own behavior changing, not sampling noise).

**Disconfirming test, not a fix applied on faith:** continued pilot 2's honest (non-peak) checkpoint with everything unchanged except a cosine LR decay, `3e-3 → 3e-5`. Two named predictions before running it — damping tracks the LR cut (recipe) vs. oscillation persists at the floor (architecture). Result: amplitude `0.04-0.06 → 0.000`, locked to perfect accuracy, damping visibly tracking the schedule rather than merely coinciding with training running longer. Recipe confirmed (`RECIPE_LOG.md` has the full test and numbers).

**Batch size (64) checked and ruled out before touching anything** — not the tiny-batch bounce scenario — so the test isolated one variable.

**Consequence, and why this is the second time "measure it again on a competent model" mattered more than the number it replaced:** every S*/rank/budget number in this document before 2026-08-22 was measured on checkpoints now known not to represent stable competence. The re-run under the corrected schedule produced the first genuinely stable pilots this project has had — criterion holding at every evaluation from `S*` to the terminal checkpoint — and both PR measurements *tightened* by an order of magnitude in cross-seed spread (query PR: 14.3 → 0.97; causal PR: 9.9 → 0.93) compared to the unstable measurement. The earlier instability wasn't only a competence problem; it was corrupting the geometry measurement §3.1.5/§3.3 depend on, silently, in a way that produced numbers confident enough to nearly get written into `PREREG.md` as final twice.

### 5. The instability was corrupting the geometry, not just the accuracy — the fourth instance of this pattern

Worth its own line rather than a closing sentence on finding 4, because it's a recurring failure mode across this project, not a one-off: **a measurement kept turning out to be of something other than what it named.** The prior project's original participation-ratio estimate (~15) was taken at chance accuracy — the reason "measure again on a competent model" was this project's founding instinct rather than an afterthought. This session found the same shape three more times: causal PR measured and reported as if it were query PR, and the reverse (finding 2); "reached criterion" measured under a soft gate when §2.2 specifies a hardened one (finding 1); and now, `S*`, causal PR, and query PR all measured on a network that hadn't finished reorganizing itself.

The numbers make this one unambiguous rather than merely suspected: query PR's cross-seed spread went from 14.3 to 0.97, causal PR's from 9.9 to 0.93 — roughly an order of magnitude in both, purely from letting the network reach a stable solution before measuring it. Both `S*` and `rank` — the two quantities the entire real-seed launch depends on — were being read off checkpoints mid-reorganization, twice, before this was caught. Neither prior measurement was a rough approximation of the right answer; both were confident, precise readings of the wrong thing.

**Resolved, not open anymore:** §3.1.7's throwaway pilot ran to completion — `S*=15,900`, well below the official pilots' 25,600, so the training budget (102,400) stands unchanged. Competence survives the rank-36 bottleneck.

### 6. Generator speedup: two working fixes, one that looked right and thrashed anyway

Profiling found the generator's ~1,370ms/batch dominated by `random.randrange()` overhead (58%) and `_generate_arm_c` rebuilding an independent ~1,020-item pool the item already had a perfectly good one for (28%). First fix attempt (buffer symbol draws through numpy) made things *slower* (2,910ms/batch) — numpy's speed is in vectorized bulk operations, and per-element access from a Python loop pays numpy's C→Python boxing on top of the Python-loop overhead it was meant to remove. Root cause correctly diagnosed, reverted, tried again: bulk-generate through numpy, convert the *entire* buffer to a plain Python list with one `.tolist()` call, then consume via ordinary list indexing — no numpy touched after the refill. That version worked, ~3.7x faster at the primitive level.

Integrating it back into the full pipeline surfaced a second bug the isolated benchmark couldn't show: the same buffered RNG serves both symbol draws (alphabet size 64) and position selection in `_flip_positions` (alphabet size 3, added while fixing that function's own `random.sample()` cost), and a single buffer keyed to "the last alphabet size used" thrashed — invalidating and refilling on every alternation between the two call sites, worse than either `random.randrange()` or `random.sample()` alone (2,758ms/batch, the worst of any version tried). Keying the buffer by alphabet size instead of holding one shared buffer fixed it. Final, clean, uncontended measurement: **311ms/batch, a 4.4x improvement** — verified only after specifically re-testing end-to-end in the full pipeline, not trusting the isolated micro-benchmark that looked clean.

Three consecutive "should be faster" changes, one net regression caught and reverted, one net regression caught and fixed in place, before landing on a real 4.4x. Worth its own line for the same reason finding 4 was: an isolated benchmark reading "faster" does not mean the change is faster where it actually runs.

**This is the fifth instance of the pattern finding 5 named, and the clearest one yet.** The `_flip_positions` fix was verified correct on its own — the isolated microbenchmark for bulk-generate-plus-`.tolist()` genuinely showed ~3.7x. It was the *integrated* path, two call sites sharing one buffer keyed to a single alphabet size, that did something the component-level test had no way to show. Same shape as the gate-hardening bug (finding 1): a piece verified correct in isolation while the assembled system quietly did something else. The general lesson, stated plainly so it doesn't need re-deriving next time: **never accept a component-level speedup — or any component-level result — without re-measuring the whole pipeline it feeds.** A clean microbenchmark is evidence about the microbenchmark, not about the system.

### 7. Canary run clears, but S* came in 50% higher than the throwaway pilot predicted (2026-08-22)

The first real seed (Regime 1, arms A+D, rank=36, full 102,400-step budget) is the first genuinely apples-to-apples test of `S*=15,900` from §3.1.7's throwaway pilot — same rank, same criterion, but a real seed instead of a discarded one, and 7x the step budget available to reach it. It landed at **`S*=23,800`**, not near 15,900.

This is not a repeat of findings 1-6 — nothing was measured wrong. Both numbers are honest onset-of-stable-competence reads on their own runs; they just disagree, by about 50%, on a single seed each. The gap is worth naming rather than letting `15,900` stand unqualified as "the" number, because it's exactly the kind of single-seed variance §2.6's move to 3 seeds per regime exists to characterize. `S*` still leaves more than 3x headroom before the 102,400 cap either way, so nothing about the budget itself is threatened — but treat `15,900` as what it always was, a single discarded pilot's number, not a prediction of where real seeds will land.

Query PR came in closer: `26.99` against the pilot's `27.99`, both comfortably below `rank=36` — the bottleneck-headroom finding replicated even though `S*` didn't.

**That contrast — geometry tight, timing loose — is worth stating on its own, not just as a footnote to the S* gap.** §3.3 already flagged the general shape from watching a single pilot mid-training ("participation ratios converging across all three [pilot] seeds *while one was still at 0.88 accuracy*: representational geometry stabilizes before behaviour does"). This is the same pattern, seen across two independently-trained runs rather than within one training trajectory, with a cleaner number attached: a 50% swing in *when* the network stabilizes produced under a 4% swing in *what* it stabilized to. Good news for §6.1's claims specifically, since those depend on the causal subspace being a stable property of the task rather than an artifact of one training run's particular path. **Not yet §3.3's actual seed-spread result** — that requires all three Regime 1 real seeds, not one real seed against one discarded pilot — logged here only so the pattern is on record before the remaining seeds arrive, not reconstructed from memory once they do.

### 8. First Regime 2 real seed stabilized 3.2x faster than Regime 1's canary (2026-08-23)

`real_seed_r2_0` (all five arms, the new abstain head, otherwise identical rank/budget/schedule to `real_seed_r1_0`) reached `S*=7,500` — against Regime 1's `23,800` on the same seed index. The abstain head itself converged fast and stayed there: BCE loss and per-batch accuracy both saturated (≈0 loss, 1.0 accuracy) from roughly step 700 onward, holding through the terminal checkpoint. Query PR (`28.58`) and causal PR (`26.92`) both landed in the same `26-29` cluster as the other three real-data points so far (§3.1.7's pilot, `real_seed_r1_0`) — the geometry-tight/timing-loose pattern from finding 7 held again, this time across regimes rather than across seeds.

**One seed per regime is not evidence the effect is regime-general** — this is exactly §2.6's "one regime with three seeds is interpretable, two regimes with one seed each is not" concern, now showing up as a real number rather than a hypothetical. Logged here, not in `PREREG.md`'s numbers, specifically so it isn't quietly treated as established once `R1seed1`/`R2seed1` arrive.

Worth naming a plausible mechanism without asserting it: Regime 2 trains on B1/B2/C in addition to A/D, and those arms include short, quickly-satisfiable examples (arm C's `rho=0` items supervise only the abstain head, no retrieval steps at all) — more, and more varied, gradient signal per wall-clock step could plausibly speed early optimization independent of anything specific to abstention as a capability. Equally plausible: pure seed variance, no regime effect at all, and `R1seed0`'s `23,800` or `R2seed0`'s `7,500` (or both) is simply where that particular seed's optimization landed. Nothing here distinguishes those two explanations — that is what the remaining four seeds are for.

**Update, second Regime 2 seed (2026-08-23): `real_seed_r2_1` reached `S*=3,000`.** Both Regime 2 seeds now sit far below both Regime 1 seeds — `[23800, 23800]` vs `[7500, 3000]`, no overlap at all — which is a materially stronger signal than the single-seed version of this finding above. Still four data points, not the six §2.6 commits to, but a regime effect on stabilization speed is now the better-supported explanation than pure coincidence. **Not yet claimed as settled**: `real_seed_r1_2` and `real_seed_r2_2` are what would make this a real 3-vs-3 comparison rather than 2-vs-2.

**Final update, full six-run matrix complete (2026-08-23): `real_seed_r2_2` reached `S*=3,000`, matching seed 1 exactly.** The complete comparison, all 3 seeds per regime:

| | S* | causal PR | query PR |
|---|---|---|---|
| Regime 1 | `[23800, 23800, 24800]`, spread **1,000** | `[25.352, 25.362, 25.353]`, spread **0.010** | `[26.985, 26.986, 26.983]`, spread **0.003** |
| Regime 2 | `[7500, 3000, 3000]`, spread **4,500** | `[26.921, 26.343, 27.263]`, spread **0.920** | `[28.580, 27.824, 28.946]`, spread **1.122** |

No overlap between the regimes on `S*` at all — every Regime 2 seed stabilized faster than every Regime 1 seed. That is now a well-supported finding, not a coincidence: 3 vs 3, not 1 vs 1.

**A second pattern emerges only with the full set, not visible in any pairwise comparison above: Regime 1 is tight on every axis, Regime 2 is loose on every axis.** Regime 1's spreads (1,000 / 0.010 / 0.003) are dramatically smaller than Regime 2's (4,500 / 0.920 / 1.122) across all three quantities — timing *and* geometry. This is the opposite of what finding 7/9 established as the general pattern (geometry tight, timing loose, *within* a regime) — here the axis that varies is *between* regimes, and Regime 2 is simply noisier across the board. Plausible mechanism, not asserted: Regime 2's more varied training distribution (five arms of differing structure and difficulty, versus Regime 1's two nearly-identical ones) gives each seed more room to find a different specific solution, even though all three still land in a materially faster, materially tighter time-to-competence than any Regime 1 seed. Both query PR maxima (Regime 1: 26.986, Regime 2: 28.946) stay well clear of `rank=36` — the bottleneck has slack in both regimes, this pattern doesn't threaten that conclusion.

**Correction (2026-08-23): the PR-tightness half of the paragraph above needs finding 10's context.** "Regime 1 tight / Regime 2 loose" bundles `S*` spread and PR spread together as if they were the same kind of evidence, and finding 10's untrained-baseline check shows PR has some inherent cross-seed stability on this fixed architecture even before training — so PR spread differences between regimes are not purely a "regime effect."

**Second correction (2026-08-23), on direct challenge: "no overlap" is not a claim this finding is entitled to make, and neither is "Regime 2 is noisier on timing."** `S*` is a threshold-crossing statistic on a 128-item validation set, and finding 10 showed three of the six seeds' `S*` were set by a one-item margin. That instrument limitation doesn't stay contained to individual numbers — "no overlap between `[23800,23800,24800]` and `[7500,3000,3000]`" is built entirely out of those same numbers, so it inherits the same limitation, not immunity from it because the ranges happen to be disjoint.

What survives: the *gap* is large — roughly eightfold, `~3,000` versus `~24,000` — far bigger than a one-item threshold wobble on a 100-step checkpoint grid could plausibly produce on its own. That's worth stating as an approximate, order-of-magnitude difference, instrument limitation named up front, not walked past.

What does not survive: the precise spreads (`1,000` vs `4,500`), the "no overlap" framing as a crisply-resolved comparison, and especially "Regime 2 is noisier on timing" as a property of the regime. The likelier explanation is curve-steepness at the moment each regime happens to cross threshold: Regime 2 crosses early, while accuracy is presumably still climbing steeply, so a one-item wobble shifts the measured `S*` by many checkpoints; Regime 1 crosses later, plausibly on a flatter part of the curve, so the same wobble barely moves it. That alone would produce exactly the tight/loose pattern observed, with no regime-level "noisiness" required as an explanation — a coarse threshold on a fast-moving curve manufactures spread that a coarse threshold on a slow-moving curve does not. The corrected claim: **Regime 2 stabilizes roughly an order of magnitude faster than Regime 1 — the within-regime spread numbers and the "noisier" characterization are retracted, not merely caveated.**

**Six-run commitment (§2.6) fully satisfied.** All findings above (this one and finding 9) are now based on the complete, preregistered sample — not partial data pending confirmation.

### 9. Two Regime 1 seeds landed on the exact same S* (2026-08-23) — verified genuine, not a duplicate-run bug

`real_seed_r1_1` reached `S*=23,800` — the identical checkpoint index as `real_seed_r1_0`. Causal PR (25.36 vs 25.35) and query PR (26.99 vs 26.99) are likewise nearly indistinguishable. An exact match on a 100-step checkpoint grid across 102,400 steps was surprising enough on its own (roughly 1-in-1,000 by chance if S* were uniformly distributed across checkpoints) that it was checked before being logged as a result rather than a bug, following the standing lesson from findings 1-6: an implausible-looking number gets verified, not reported on faith.

**Checked and ruled out as a duplicate:** step-0 loss differs (7.3425 vs 7.3834), the step-500 val_acc dip differs in shape and magnitude (seed 0 drops to L2=0.758/L3=0.719; seed 1 drops to L2=0.898/L3=0.906), the full trajectories differ at every logged step in between, and the two `.pt` checkpoint files have different content hashes. These are genuinely two different training runs, from different `torch.manual_seed` values and different data-generation seed streams, that independently converged to the same stabilization point.

**What actually happened at that point:** both runs show their own *last* failing checkpoint at step 23,700 — both dipping to L3=0.945, one hundredth below the 0.95 criterion — then both hold PASS from 23,800 through their respective terminal checkpoints (78,600 and 78,700 steps later, with no further failures on either). The synchronization is not explained by a trivial "waiting for the LR schedule to anneal" story: `lr_at(23800) ≈ 2.62e-3`, only 13% decayed from the 3e-3 peak, nowhere near the floor.

**Not yet interpretable with two data points.** Either `23,800` is a real structural boundary this task/architecture combination converges toward regardless of seed (which would be a genuinely interesting finding about the training dynamics), or two independent seeds coincided by chance and a third will land somewhere else entirely. `real_seed_r1_2` is the run that distinguishes these — logged now so the coincidence is on record before that seed's result either sharpens it into a pattern or dissolves it into noise.

**Weak evidence against the structural-boundary reading, from Regime 2 (finding 8's update):** `real_seed_r2_1` reached `S*=3,000` against `real_seed_r2_0`'s `7,500` — a 2.5x spread between two seeds trained under the identical schedule, rank, and step cap that produced R1's exact match. If `23,800` (or some other fixed step) reflected a genuine architectural/schedule boundary independent of training data, Regime 2's seeds would be expected to cluster near their own common value too, not spread 2.5x. They don't. This doesn't resolve the R1 coincidence — Regime 1 and Regime 2 are different training distributions, so a mechanism specific to one regime isn't ruled out — but it weakens the "universal boundary" reading somewhat in favor of "R1 seeds 0 and 1 coincided." `real_seed_r1_2` remains the direct test.

**Resolved (2026-08-23): `real_seed_r1_2` reached `S*=24,800`, not `23,800`.** The third Regime 1 seed landed close to — but distinctly different from — the first two, settling this in favor of the coincidence reading over the structural-boundary reading. All three Regime 1 `S*` values: `[23800, 23800, 24800]`. The near-exact match between seeds 0 and 1 really was two independent runs happening to land within one checkpoint-grid step of each other (100 steps out of a 102,400-step budget), not a hidden determinism or an architectural constant. §3.3's actual seed-spread deliverable is now complete with the real numbers: query PR `[26.985, 26.986, 26.983]` (spread 0.003) and causal PR `[25.352, 25.362, 25.353]` (spread 0.010) — both dramatically tighter than `S*`'s spread (1,000 steps, ~4% of the mean). This confirms finding 7's pattern a third time, now across a full 3-seed set rather than a single pair: **geometry converges to essentially the same solution regardless of seed; the number of steps it takes to get there does not, and the two must not be read as if they were the same kind of quantity.**

**Correction (2026-08-23): the paragraph above overclaimed "settled."** Challenged directly, on grounds that PR this tight (4 significant figures) across independently-seeded runs "is not what real seed variation produces" and could indicate the seeds weren't actually varying. That challenge produced finding 10 below — a real, sharper coincidence than the one this finding originally reported, and one that is genuinely still unresolved rather than closed by seed 2's result. Read finding 10 before treating this finding's "geometry converges to the same solution" framing as fully earned.

### 10. Challenged on Regime 1's PR tightness — no seeding bug, but the framing needed correcting, not just defending (2026-08-23)

Direct challenge to finding 9's "geometry converges to essentially the same solution" claim: query PR `[26.985, 26.986, 26.983]` and causal PR `[25.352, 25.362, 25.353]` across three independently-seeded runs is tight enough — identical to 3-4 significant figures — that it could indicate a seeding defect (init seed not threaded, or all three runs sharing a data stream) rather than genuine convergence. Three checks followed, none skipped, none taken on faith.

**Check 1 — is the seeding mechanism actually broken? No.** Fresh construction of `GatedCacheModel` at seeds 1000/1001/1002 (matching `torch.manual_seed(1000 + pilot_idx)`) produces genuinely different initial weights — pairwise L2 distances comparable to each tensor's own norm, across every parameter. The three *trained* checkpoints (`real_seed_r1_0/1/2.pt`) diverge just as much: overall model-wide distance ≈145 versus an overall weight norm ≈114 — the three trained models are about as different from each other as three unrelated points of similar scale would be. One parameter is a genuine outlier: `gate.combine` (a 4-parameter `nn.Linear(3,1)` fitting two already-batchnormed scalars and their product) converges to within ~3% relative distance across seeds — but a 4-parameter fit on normalized features has far fewer distinct good solutions than a 512×36 or 36×64 matrix does, so tight convergence there is the architecturally expected outcome, not a red flag. No seeding bug found, in init or in training.

**Check 2 — is tight PR itself just an artifact of training converging everyone to the same point? Also no, but the real answer is more nuanced than that.** Measured causal/query PR on three *untrained*, freshly-initialized models (same seeds, same geometry-split batch used throughout the project): causal PR `[15.43, 16.58, 16.87]`, query PR `[21.73, 21.44, 22.27]`. Training moves both quantities up substantially and consistently (+9-11 points causal, +5-7 points query) — this is real, learned structure, not an architectural artifact masquerading as one. **But** the untrained values are already fairly tightly clustered — untrained query PR spread (0.83) is comparable to, even larger than, Regime 2's *trained* spread (1.12). PR, as a measurement on this fixed architecture (`rank=36`) against a fixed reference batch, has some amount of built-in stability across random seeds even before any training happens. Findings 5, 7, and 9's framing — "geometry is a stable property that training converges to" — is not wrong, but it overstated how much of the tightness is specifically about training convergence versus how much is inherent to the measurement itself on this fixed setup. That distinction was not made anywhere before this check, and should have been.

**Check 3 — is there a shared hard item driving the exact 121/128 (L3) match at all three seeds' last-failing checkpoint?** (Separately noticed while responding to the challenge — a sharper, more specific version of finding 9's original coincidence than "S* landed near the same step": all three Regime 1 seeds' *last failing* checkpoint showed exactly 121/128 correct at L=3, one item short of criterion, versus Regime 2's much more varied margins — 6, 27, and 1 items short across its three seeds.) Checked at the *terminal* checkpoints (the only ones with saved weights — the exact step-23,700/24,700 states are gone, overwritten by the atomic resume-checkpoint scheme) via per-item retrieval margin rather than raw accuracy, since all three terminals are 100% correct and accuracy alone carries no information at that point. Result: the lowest-margin items barely overlap across the three models (0 of the lowest 5 shared; 2 of the lowest 10 shared pairwise, none across all three) — weak evidence *against* a validation-set-intrinsic hard item, but this checks the fully-converged state, not the historical near-miss checkpoint, so it does not resolve the coincidence either way. **The 121/128 three-way match remains genuinely open** — logged here rather than explained away, since a negative result on a different checkpoint than the one in question isn't a resolution.

**Consequence — `N_VAL` raised from 128 to 1,024 for all evaluation passes from here forward** (`model/pilot_train.py`). 1/128 granularity against a 0.95 criterion and a §5.3 abstention budget of 5 percentage points is coarse enough that a single item flips pass/fail — exactly the instrument-noise concern this whole investigation traces back to. The six completed real seeds keep their `S*` as measured on the old, coarser instrument; re-running them was considered and explicitly declined — `S*` sized a training budget with roughly 4x headroom and gates nothing else, so sharpening it does not pay for the compute it would cost, especially with Phase 3 (Q2, the actually load-bearing untested question) still ahead. Every evaluation from Phase 2 onward uses the finer instrument.

### 11. Regime 2 checkpoints guess END-flagged entries ~2x more often than Regime 1 under a foreign cache (2026-08-23)

A secondary signature surfaced while running §4.1's leakage check, flagged in advance as a specific risk to watch for: with `MIN_END_DECOYS=8` plus each item's own true terminal, every cache carries exactly 9 END-flagged entries out of `N≈1022-1024` — a model that gives up on an unfamiliar (shuffled/foreign) cache and falls back to "guess among the END-looking entries" would land on one at a rate near `9/N≈0.88%` if guessing uniformly among them, well above the `1/N` rate of guessing uniformly among *all* cache entries.

Measured directly: **Regime 1 checkpoints land on an END-flagged entry 2.8-3.3% of the time under a foreign cache; Regime 2 checkpoints land on one 6.9-7.9% of the time — both well above the 0.88% nominal rate, and Regime 2 consistently roughly double Regime 1, across all three chain lengths and all six checkpoints.** Plausible mechanism: Regime 2 was explicitly trained to recognize dead ends (B1/B2/C → ABSTAIN), so its query mechanism may have learned a genuine "when nothing looks right, prefer terminal-looking entries" fallback that Regime 1 — never trained on a single dead end — has no reason to develop. Not asserted as confirmed; Phase 3 (§5.4, comparing the trained abstain head against the §2.2 gate quadrant) is the actual test of whether this reflects a real dead-end-sensitive representation or a shallower correlate.

**Does not affect the §4.1 leakage verdict.** Landing on *an* END-flagged position is a different event from landing on the *specific* position matching the true target — the primary accuracy metric stayed at nominal chance in every case regardless of this elevated rate, exactly as predicted before running the check: the two are separate questions, and an elevated END-guess rate should be reported as a behavioral finding, not mistaken for above-chance leakage.

### 13. §4.3 fails its own preregistered criterion — top-1 accuracy saturates to exactly 1.0000, AUROC undefined (2026-08-23)

`model/phase2_margin.py` measured teacher-forced per-step retrieval accuracy and margin AUROC on held-out arm-A items across all six checkpoints, all three chain lengths. Result, uniform across every checkpoint and every `L`: **top-1 accuracy = 1.0000, zero incorrect retrieval steps out of 294,912 pooled teacher-forced steps** (49,152 per checkpoint: 8,192 items × `L` summed over `L∈{1,2,3}`, times 6 checkpoints). §4.3 preregisters accuracy within `[0.60, 0.98]` — `1.0000` is outside that window. Margin AUROC needs both a correct and an incorrect class to be computable at all; with zero incorrect steps in a sample this large, it is undefined, not merely below the `0.70` threshold.

**This is a coherent consequence of task structure, not an obviously broken measurement.** There is no error-correction across hops — a wrong retrieval at any single step propagates forward with nothing to recover it. §3.2's whole-walk exact-match gate (≥95%, held stable from `S*` through the terminal checkpoint) is therefore a much harder bar than any single step's accuracy: even a modest per-step error rate compounds multiplicatively across up to 3 hops and would drag whole-walk accuracy well below 95%. A checkpoint that reliably clears §3.2's gate is close to structurally required to show near-100% per-step accuracy on the same in-distribution (arm-A) data §4.3 measures against. The criterion's `[0.60, 0.98]` window looks like it was calibrated expecting daylight between per-step and whole-walk accuracy that these fully-converged, budget-exhaustion checkpoints don't have.

**Reported as a genuine failure, not reinterpreted into a pass — this was an explicit decision, not a default.** §4 states all three checks must pass before any coverage or recursion claim; asked directly how to handle a check that fails for a structurally coherent reason, the answer was to log it exactly as measured and hold §4 as not fully cleared, rather than reason around it to let Phase 3 proceed. §4.1 and §4.2 both passed cleanly (findings above); §4.3's failure is specific to itself and does not average out against the other two.

**What this means going forward, stated plainly so it isn't quietly worked around later:** Phase 3/4 do not proceed on the strength of §4.1/§4.2 alone. Resolving §4.3 — whether by remeasuring at a different point in training, revisiting whether the criterion transfers to a task this saturable, or some other explicit decision — is required before a coverage or recursion claim can be made, per §4's own stated rule.

### 16. P1's raw AUROC was almost entirely an integration-count shortcut, not encoded dead-end status (2026-08-24)

P1's raw numbers from finding 15 (`0.687` combo1, `1.000` combo2) looked, on their own, like P1 might be an *easier* signal than P2 in one combo and *harder* in the other — an odd, unexplained asymmetry. The actual explanation is a shortcut, and it was checkable directly from §2.5's own `ρ` definition without touching the model at all.

**The mechanism, confirmed against the generator before touching model output at all:** arm A's `ρ = L−1` is *fixed* for a given `L` — every A item has the same integration count. Arm B2's `ρ = j` (the corrupted hop index) varies per item — and at `L=2` specifically, the generator's own hop-selection draw (`hop_j = randrange(1,L)+1`) collapses to a single deterministic value, `hop_j=2` always (verified directly: 2,000/2,000 draws at `L=2`, all `ρ=2`; at `L=3`, `ρ` splits 972/1,028 between `2` and `3`). At the training config (`L=2`), this means arm A's integration count (`1`) and arm B2's (`2`) are *both perfectly constant and different* — a trivial linear separator exists in the count alone, no state content required. At `L=3`, half of B2's items now share A's count (`2`) exactly, so a count-based classifier would misclassify roughly half of them.

**That mechanism predicts the exact observed pattern before any residualization is run:** perfect separation at the training config and at the band-transfer test (same `L=2`, so the same deterministic counts hold — predicts `combo2 raw ≈ 1.0000`, observed `1.0000`), degraded separation at the `L`-transfer test (new distribution with 50% count overlap — predicts a real drop, observed `0.6872`).

**Residualizing state-probe score against `pos1_integration_count` (same OLS-residual, same bootstrap-CI treatment as P2's margin regression) confirms it directly:**

| | raw AUROC | count-only AUROC | count-residualized AUROC [95% CI] |
|---|---|---|---|
| P1, combo1 (`L=2→3`) | 0.6872 | 0.2403 | `0.4711` `[0.4531, 0.4884]` |
| P1, combo2 (`1021→256`) | 1.0000 | 0.0000 | `0.4930` `[0.4728, 0.5129]` |

**Once the count shortcut is controlled for, P1's residual signal is at or below chance in both combos — the CI for combo1 doesn't even reach `0.5`.** (Combo2's `count_only_AUROC=0.0000` is not a bug: at `L=2`, higher count deterministically means arm B2, so count alone perfectly anti-predicts the "answerable" label — an AUROC of exactly `0` is the correct value for a perfect inverse separator, not an error.) There is no evidence, from this canary, that state at P1 encodes anything about dead-end status beyond a trivial hop-count readout that has nothing to do with the model's internal representation — the count is a property of *which items got sampled*, not of what the network learned.

**Reported as a result against §5.1's own preregistered P1 question, not merely as a control that failed — this does not retroactively touch any preregistered threshold, and P1 never had one.** §5.1 asked, at P1, whether state encodes that the committed value isn't itself a key, before the disproving lookup resolves. Answer, on this checkpoint: not linearly, and not beyond what integration count already gives away for free. **Correction (2026-08-24): the comparison originally drawn here — that P2's signal survived an analogous control while P1's didn't — no longer holds.** Finding 19 later applied the full control set (margin, END-flag identity, count, separately and jointly) to P2 as well, on both regimes, and P2's signal collapsed to chance too once END-flag identity and count were controlled for alongside margin. Neither preregistered probe position has shown state-level signal surviving its full confound set, on either canary checkpoint measured so far.

The band check's "not confounded" claim is only as meaningful as this finding's "there's something here to be confounded with" — reported together so neither is read as stronger than it is on its own.

### 21. §1.3's lower bound depends on which dimension you count, and the raw-width reading was too generous (2026-08-24)

§1.3 justifies its bounds by noting raw element width (16 bits/dimension, `fp16`) overstates true recurrent capacity — stated reasoning: this "cuts in favor of these bounds." That justification only covers the **upper** bound (`cache_bits/state_bits ≥ 4`, where overstating `state_bits` makes the bound *harder* to satisfy, so passing it despite the overstatement is conservative). For the **lower** bound (`state_bits/trajectory_bits ≥ 16`), overstating `state_bits` makes it *easier* to satisfy — the same justification cuts the other way, and §5.4's informative-null clause depends on the lower bound specifically. This was never checked before finding 19 cited the raw-width figure.

**Two figures, computed and reported side by side, per instruction — the raw-width number is kept, not replaced:**

| dimension substituted for `d_model×d_state` (512) | value | `state_bits` | `lower_bound_ratio` | clears `16×`? |
|---|---|---|---|---|
| raw width (existing, `generator/capacity.py::PROPOSED`) | 512 | 8,192 | **99.9** | yes |
| causal PR (R1 terminal checkpoints, ≈25.35) | 25.352 | 405.6 | **4.95** | **no** |
| query PR (R1 terminal checkpoints, ≈26.98) | 26.985 | 431.8 | **5.27** | **no** |
| `rank` (§3.1.5's architectural bottleneck, the most generous of the three substitutes) | 36 | 576.0 | **7.02** | **no** |

**Causal PR is the substitute used as primary, and the reasoning is stated plainly: the lower bound's `state_bits` term is about the full recurrent state's effective capacity, and causal PR is specifically defined as the participation ratio of the *whole flattened state's* causally-relevant subspace (`model/geometry.py`) — the most direct measured stand-in for "how many dimensions of state actually carry information" that this project has.** Query PR is a narrower, derived quantity (the query projection's own output, not the state); `rank` is an architectural ceiling, not a measurement of what the state actually uses. **All three effective-dimension readings fall below `16×` — the most generous of them, `rank`-based, clears less than half the floor.** This is the outcome to state now, before the remaining four seeds land, exactly as it was computed, not adjusted after seeing whether it was convenient: **if the P2/abstain-head null (findings 19, 20) holds through all six seeds, it is not entitled to the strong reading of §5.4's clause** ("ample room, and it went unused"). Under the effective-dimension reading, the accurate framing is **capacity-ambiguous**: state may not have had meaningfully more room than a pointer needed in the first place, so a null is still consistent with "the architecture never gave it anywhere to put this" rather than "the architecture gave it room and it declined." Both are legitimate readings of a null; only the raw-width number licensed the stronger one, and the raw-width number was measuring the wrong thing for this specific clause.

**This does not retroactively touch §1.3's original bounds as preregistered** (both bounds were, and remain, satisfied under the raw-width computation that was actually specified) — it is a recomputation of a quantity §5.4 leans on for *interpreting* a null, using a stated, defensible substitution, logged as a method rather than smuggled in as a threshold change. `AMENDMENTS.md` #3 has the log.

### 24. Positive control, corrected: it confirms the instrument reads margin and count, not that it can read status beyond them — the instrument question is still open (2026-08-24, corrected same day)

Post-hoc methodological control, per §8, explicitly not an arm, not a seed, never contributing to any Q2 result. §2.1: "A tempting response is to build an explicit register holding hop count, last margin, and value-validity, and point the probe at it. Do not... a probe that finds coverage in a channel built to carry coverage has measured the architect, not the model." This control deliberately builds exactly that forbidden channel and points the identical probe pipeline at it.

**Implementation choice, logged (`AMENDMENTS.md` #5): the register was appended as extra probe input features on an existing checkpoint (`real_seed_r1_0`, no new training) rather than built into a separately-trained model.**

`model/phase3_positive_control.py`: `[pos2_state ; pos2_margin ; pos2_is_end ; pos2_integration_count]` fed to the same `fit_linear_probe`, on the same combo1 (`L=2→3`) items as findings 15/19.

```
augmented-feature probe: train_AUROC=1.0000  test_raw_AUROC=0.9992  JOINT_resid=0.5008[0.483,0.518]
plain (unaugmented) state probe, same items: raw_AUROC=0.9976
```

**Original write-up called the residualized number "expected and not informative." That was wrong, caught on direct challenge, and the finding's own headline claim — "the null found elsewhere is about the model, not a silently broken instrument" — does not follow from this result and is withdrawn.**

The register's three components were `[margin, is_end, integration_count]` — and the joint residualization control is `[margin, END-flag(=is_end), integration_count]`, **the identical three quantities, not two of three.** `is_end` was used as the stand-in for §2.1's "value-validity," but it is the same variable already being regressed out as the END-flag confound, not a distinct signal. Residualizing the register's own linear combination against the exact numbers it was built from drives the residual toward zero by construction — the collapse to `0.5008` is not a discovery about the model or the instrument, it is arithmetic. **This control, as built, tested only whether the pipeline can detect margin and count — never in question — and said nothing about whether it can detect a status-like signal distinct from them.**

**Consequence, stated plainly: the instrument-sensitivity question this control was built to close is still open.** It is *not* established that the P2/gate/abstain-head nulls (findings 19, 20, 23) reflect the model rather than a probe insensitive to genuinely status-like, as opposed to confound-shaped, signal. Findings 22's and this finding's earlier claims to the contrary are corrected here, not merely caveated.

**What this control does establish, and it is real: raw AUROC `0.9992` on a channel built from margin/count/end-flag confirms the pipeline correctly reports near-ceiling discrimination for confound-shaped signal.** That eliminates one failure mode (the capture→probe→AUROC arithmetic silently returning chance regardless of input) without eliminating the more relevant one (a linear probe missing a status signal a nonlinear or distributed encoding would carry) — see finding, `AMENDMENTS.md` #5's extended entry, and Task 2's limitation below.

**Side observation, unaffected by the correction:** the plain, unaugmented state probe on the same items already reads `0.9976` — barely below the augmented version's `0.9992`. **A second, structural limitation, independent of Task 1's result and worth stating regardless of how it had come out: an externally computed, noiseless, axis-aligned register handed directly to a linear probe is the easiest possible object for that probe to read.** A model that had genuinely *learned* to encode status would most plausibly encode it distributed and entangled across many state dimensions, not as a clean external channel appended after the fact — and this control does not speak to whether a linear probe would find *that*. This control establishes a floor on instrument sensitivity (it can read clean, confound-identical signal), not a ceiling (it says nothing about messier, learned, distributed encodings). Logged in `AMENDMENTS.md` #5 alongside the original post-hoc-append reasoning.

### 25. Meta-finding: three preregistered items failed not from vagueness but from precision that turned out not to bind

Three separate pieces of preregistered text, caught only at the moment of execution, each already logged individually — consolidated here because the pattern across them is itself a finding, not just three unrelated incidents:

1. **§4.3's `[0.60, 0.98]` top-1 accuracy window** (finding 13). Precisely specified — an explicit numeric range, not a vague "reasonably accurate" — and arithmetically unsatisfiable by any checkpoint that also clears §3.2's whole-walk `≥95%` gate: no error-correction across hops means passing the harder criterion forces per-step accuracy that structurally exceeds `0.98`. Not a close miss on one seed; `1.0000` on every one of six.
2. **§1.3's lower bound, `state_bits ≥ 16 × trajectory_bits`** (finding 21). Precisely specified and precisely computable — a clean formula, real numbers, both bounds satisfied as literally written (`99.9×`, comfortably above the stated floor). It passed exactly as operationalized, and still failed to deliver the protection it was written to provide: the raw-element-width computation it specified is the wrong instrument for what §5.4 leans on it for, and the bound clears easily only because it's measuring architecture, not the state's actual effective capacity, which falls to `4.95-7.02×` under the reading that measures what the clause actually needs.
3. **§2.4's "preregister the prediction and the direction"** (finding 23, `AMENDMENTS.md` #4). Here the text was precise about *what* needed to be done — an explicit instruction to state a specific, falsifiable claim before data existed — and nothing was ever written to satisfy it. The instruction bound nothing because no one closed the loop it opened.

**The common thread is not that any of these three was underspecified.** All three are exactly the kind of concrete, numeric, checkable language this project's own discipline has repeatedly insisted on over vaguer alternatives. What failed was a further-out assumption in each case: #1 assumed some daylight between per-step and whole-walk accuracy that this task's error-correction-free structure doesn't have; #2 assumed raw element width was a reasonable stand-in for effective capacity, true for the upper bound and false for the lower one it was also applied to; #3 assumed that instructing a future measurement to preregister a value was the same as the value existing. **Precision in the sentence does not guarantee the sentence binds the situation it was written for — that has to be checked separately, and in all three cases here it was checked only when the measurement was actually attempted, not before.**

**Not a reason to distrust precise preregistered thresholds generally** — the alternative (looser, unfalsifiable language) would have caught none of these three failures at all, since there would have been nothing precise enough to fail against. It is a reason to keep testing preregistered text against the actual situation as each phase reaches it, rather than treating "this was pinned in advance" as itself sufficient — pinning is necessary, not sufficient, and precision without a check that it applies is a smaller improvement over vagueness than it looks.

**Consistent with finding 23's B2 terminal-step result, and worth stating explicitly since the user asked directly whether it is: yes, same mechanism, different arm.** Finding 23 found the gate opens on `~99.90-100%` of B2's *fake* terminal queries — evidence it doesn't discriminate on value-validity at the one step it's structurally supposed to refuse. Here, on arm A's genuine required-integration steps, the same gate is *also* open essentially everywhere sampled (`g_soft` means `0.95-1.00`, rarely approaching the `0.5` threshold even at its lowest observed value). The picture across both findings is a gate that behaves like "almost always open, except where a separate structural rule (`is_end` detection) forces it closed" rather than a gate making a close, fine-grained per-step call — §6.2's clean pass and finding 23's B2 result are two views of the same underlying behavior, not independent evidence.

**Simplification flagged per §8, logged in `AMENDMENTS.md`:** the `P(m=ρ)≥0.80` pass/fail threshold is evaluated pooled across all three chain lengths into one number per checkpoint; §6.2's text conditions the *reported distribution* on `L` explicitly (satisfied — full per-`L` breakdown above) but does not say whether the threshold itself is per-`L` or pooled. Immaterial to the verdict here since every cell independently clears `1.0000`, but logged since a future checkpoint could plausibly PASS pooled while failing at one specific `L`.

**What this does and does not establish.** This is a clean, informative gate result: §6.1 is not building its constrained-vs-free comparison on a broken premise, at least not one this measurement would have caught. It says nothing yet about whether the causal-subspace constraint actually changes recursion behavior, and nothing about `m>ρ`/`m<ρ` deviations, since none occurred in this sample — the §4.1 shuffled-cache follow-up for a possible synthesis interpretation was not run, because there was nothing to follow up (zero `m<ρ` items across 18,432).

**Bound, added on direct challenge: the `P(m=ρ)≥0.80` threshold is one-directional, and `1.0000` sits on the side that doesn't discriminate.** Below `0.80` would have established that the gate did *not* learn the follow-until-END rule — a real, informative failure mode the threshold is built to catch. But clearing it does not, by itself, establish that the gate *did* learn that rule specifically, because two different policies produce the identical `P(m=ρ)=1.0000` result on clean arm A: **(a) follow-until-END** — integrate iff the retrieved value is a genuine key — and **(b) always-integrate-unless-END** — integrate iff the retrieved entry isn't flagged END. On arm A, every retrieval succeeds and every non-terminal retrieved value genuinely is a key, so (a) and (b) coincide exactly at every `L`; nothing in this measurement can tell them apart. Phase 3 already settled which one it is: finding 23 measured the gate opening on B2's fake terminal `x` at `99.90-100%` — indistinguishable from arm A's own rate, at maximal confidence — and `x` is drawn to look like a key but has no cache entry, i.e. is *not* a key. That is policy (b), not (a). Read together, `P(m=ρ)=1.0000` has the same structural shape as finding 13's arm-A retrieval accuracy of exactly `1.0000`: what a deterministic function of `is_end` produces on data where that function's two readings never come apart, not independent evidence of a learned, discriminating controller. §2.5 itself names the degenerate case this measurement can't rule out ("a gate that always integrates becomes attention" and would overshoot `ρ`) — it doesn't overshoot here only because retrieval never fails on arm A, not because the gate is confirmed to be checking anything. **The PASS stands as operationalized and is not withdrawn** — what's bounded is what it's entitled to license beyond that.

### 27. §6.1's premise check: recursion-without-integration is real, but only in Regime 1 checkpoints, concentrated in two cells — Regime 2 checkpoints show almost none, exposure confound not ruled out (2026-08-24, corrected same day)

**Why this was run.** Finding 26 (§6.2) established `P(m=ρ)=1.0000` on held-out arm A — every trajectory takes exactly `ρ` integrations plus one forced-closed END step, zero recurse-without-integrate steps, ever. That result is about arm A specifically; §6.2 conditions on it, §6.1 does not name an arm. On direct challenge: is the vacuity global, or only true of arm A's always-present-key, always-high-margin queries? **Arm A/D: confirmed zero recursion on all six checkpoints, all three `L`** — consistent with finding 26, and now shown to extend to arm D (`ρ(D)=L−1`, same walk shape as A per §2.5).

**Regime 1: recursion is real, reproducible across all three seeds, and sharply concentrated in two specific cells — not spread evenly across B1/B2/C.**

|---|---|---|

Any behavioral difference observed between the two regimes at Phase 3 is confounded with data exposure... not purely with the presence or absence of a supervised abstention target." Arm C is fresh-state uncertainty in its entirety — its break is the item's very first query — and Regime 1 checkpoints never saw a single arm-C item during training; Regime 2 checkpoints trained on it directly, at equal frequency with the other four arms. A gate that behaves differently on data it was shown during training versus data it wasn't is not automatically evidence that training *removed a capacity* — that reads a specific mechanism into a difference the exposure gap alone could produce. **Restated as measured, not caused: Regime 1 checkpoints show substantial, reproducible recursion in these two cells; Regime 2 checkpoints show almost none, on all three seeds tested.** This stays an unplanned, genuinely interesting finding either way — it just does not, as measured here, support "training erased a capacity" over "the two regimes were never shown the same data and behave differently on data only one of them saw."

**What this does and does not establish.** This is a description of measured gate *behavior* (soft/hard output as a function of state and query), not a mechanistic account of *why* Regime 1 and Regime 2 checkpoints differ here — several candidate explanations remain open and none is confirmed: the data-exposure confound above (the leading candidate, since it requires no additional mechanism beyond "the two regimes saw different training distributions"); Regime 2's count penalty, which is explicitly scoped to arms A/D only (`forward_train_regime2`, per §2.5, never applied to B1/B2/C) and so cannot be rewarding "always integrate" on those arms directly, but could still interact with the shared gate parameters; Regime 2's retrieval loss, still computed over B1/B2/C's own valid prefix, which could implicitly reward confident-looking retrieval without ever training a mid-walk "stop" signal, since abstention is handled by a separate head reading final state, not by the per-step gate; or simply more total gradient exposure across a more diverse arm mix. **None of these is resolved here; all are flagged as open.**

**Consequence for §6.1, held for explicit review before any comparison code is written.** A causal-subspace-constrained-vs-free comparison needs real recurse-without-integrate events to have anything to measure. Given this diagnostic: arm A (§6.2) and arm D are confirmed vacuous; B2 and B1 at `L≥2` are close to vacuous (`1–5%` of items, only in Regime 1, zero-to-near-zero in Regime 2); **the only cells with substantial, reproducible recursion are Regime 1, arm C (all `L`) and Regime 1, B1 at `L=1`.** Scoping §6.1's actual measurement to those cells, now that this diagnostic's numbers are known, is exactly the kind of population choice §8 requires be made transparently and logged before it's built into comparison code — not decided silently as though it were the original plan. Held for review, not yet decided.

### 29. §2.2's gate quantile-input spec was never implemented as written, for the whole project, not just pilots — same class as finding 1, a distinct kind of gap from finding 25 (2026-08-24)

**The specification, §2.2, verbatim in intent:** "Both enter the gate as quantiles, not raw values. Each is mapped through its empirical CDF, estimated once on a frozen calibration split and never updated." Three properties named: **empirical CDF** (a rank/percentile transform), **frozen** (fit once, never updated), **calibration split** (a specific, separate data partition — not train, not validation, not test, not geometry, per §3.1's own split accounting).

**The implementation, `model/gate.py::QuantileGate`, has none of the three.** `margin_norm`/`disp_norm` are `nn.BatchNorm1d` — a Gaussian mean/variance standardization, not an empirical-CDF rank transform (equivalent only if the underlying distribution happens to be Gaussian, never verified); its running statistics update every forward pass under a momentum term (`momentum=0.05`), not frozen; and those statistics accumulate over whatever data flows through — training batches — not a designated calibration split, which `docs/phase1.md`'s own split accounting never allocates space for BatchNorm to have used correctly in the first place. `gate.py`'s own docstring calls this "a stand-in for the frozen calibration-split empirical CDF... flagged as a pilot-specific simplification." **It was not pilot-specific.** `model/task_model.py::GatedCacheModel` uses `self.gate = QuantileGate()` unconditionally — every real seed, both regimes, all six checkpoints, trained and evaluated on the identical BatchNorm-based gate, contradicting `task_model.py`'s own docstring claim that "the real CDF calibration belongs to the full Phase 1-4 protocol on real seeds, not to pilots." The stand-in was never replaced; the comment saying it would be was never revisited.

**Same class as finding 1, a different clause of the same section.** Finding 1: §2.2 says "trained soft, hardened at inference" — the evaluation path never hardened, a spec/implementation gap caught and fixed within days. This finding: §2.2 says the gate's *inputs* are calibration-split CDF quantiles — the implementation never did that, a spec/implementation gap that ran the entire project's duration, through all six real-seed trainings, uncaught until now. Both are the same failure mode (a component specified as one thing, implemented as another, load-bearing for everything built on top) applied to two different sentences in the same paragraph.

**Distinct from finding 25, and the difference matters.** Finding 25 consolidated three cases of preregistered *text* that bound to the wrong *situation* — correctly implemented exactly as written, and still failing to deliver the protection intended (§4.3's arithmetic, §1.3's raw-width justification, §2.4's missing prediction). This finding is not that. §2.2's text is not vague, not misapplied, not undermined by an unstated assumption — it was simply never built. The gap here is between the document and the code, not between the document and reality.

**What defined finding 23's quadrant boundaries, checked before any interpretation was trusted, per direct instruction not to recompute yet.** `model/phase3_gate_secondary.py::quadrant_table()` does **not** use `τ` or the hardcoded `gate_threshold=0.5` at all — its own docstring, written at the time: "Empirical-rank quantile transform (no calibration-split CDF exists yet), split at the median — §8 simplest-version stand-in, logged." It ranks the raw margin and displacement values within the pooled arm-A+B2 terminal-step population *for that measurement*, split at the 50th percentile — a second, independent approximation of "quantile-ness," built post-hoc for this one descriptive table, unrelated to whatever the trained gate's own internal BatchNorm normalization did. **This was already flagged as a stand-in when written; it is not a new gap, and it is not the same gap as the trained gate's own missing CDF** — two separate approximations of the same missing calibration-split object, used in two different places, neither verified to agree with what a real frozen CDF would have produced or with each other.

**"Gate opens on B2's `x` at 99.90-100%" and the raw AUROC (`0.489-0.508`) are direct reads of `g_t` (the trained gate's raw soft output), independent of the quadrant boundaries — traced in `model/phase3_gate_secondary.py::report_gate`.** `b2_open_frac = (b2_data["term_g_soft"] > 0.5).float().mean()` — a flat threshold on the continuous soft value, no quantile transform of any kind, no reference to `quadrant_table()`. `raw_auroc = auroc(g, label)` — a rank statistic (Mann-Whitney) on `g_soft` itself, also untouched by any threshold or quantile transform. **Both survive unaffected by whatever is or isn't correct about the quadrant occupancy table specifically** — that finding's quadrant-occupancy component is the one implicated by an approximation gap (its own, separately flagged), not its open-rate or raw-AUROC components. What neither number escapes, because it isn't a downstream analysis choice at all, is that `g_soft` itself was produced by the trained gate's actual BatchNorm-based normalization — the model exactly as trained and deployed, per this finding's first half. Whether the open-rate comparison (arm A vs. B2, both near-maximal) would look different under a real calibration-split CDF is a question about whether a *differently-trained* model's gate would behave differently — not something a post-hoc threshold change on this checkpoint could answer, and not checked here.
